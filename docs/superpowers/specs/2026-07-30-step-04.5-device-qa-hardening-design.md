# Step 04.5 — Device QA Hardening

**Date:** 2026-07-30
**Status:** Approved, implementation starting with Batch A
**Baseline:** 313 unit+integration tests, 22 UI tests, all green

## Context

Manual QA on a physical iPhone surfaced seven issues across six modules after
Step 04 completed. None are P0 — nothing crashes, loses data, or corrupts an
export. This is a deliberate quality pass, sequenced before Step 05 (AI Features
& Polish) because Step 05 adds screens that would otherwise have to be
re-parented into the new navigation structure a second time.

Work is split into three batches, ordered by ascending risk. Each batch is
independently shippable and leaves the full test suite green.

## Batch A — local correctness

Four self-contained fixes. No new concepts, no cross-module coupling.

### A1 · Templates vertical scroll indicator

**Problem:** the templates collection shows a vertical scroll indicator.

**Cause:** `makeGridView()` never disables it. The chips collection view
immediately above it does (`showsHorizontalScrollIndicator = false`), so this is
an omission rather than a decision.

**Fix:** set `showsVerticalScrollIndicator = false` in `makeGridView()`.

**Files:** `Features/TemplateGallery/TemplateGalleryViewController.swift`

### A2 · Editor Layout picker shows a wrong selection for non-grid documents

**Problem:** opening an uncommon (non-grid) template shows the editor's bottom
Layout section with a default grid layout highlighted, implying a selection the
document does not have.

**Cause:** two independent defects.

1. `LayoutPickerView(selected: viewModel.state.layout.gridTemplate ?? .twoUpHorizontal)`
   — for a `.template` document `gridTemplate` is `nil`, so the initialiser
   falls back to `.twoUpHorizontal` and renders it as selected.
2. `layoutPicker.isHidden = layout.isPolygon` — hides the picker for `.polygon`
   documents but not for `.template` ones.

**Fix:**

- `LayoutPickerView.selected` becomes `GridTemplate?`; when `nil`, no cell is
  highlighted. `setSelected(_:)` accepts an optional.
- Delete the `?? .twoUpHorizontal` fallback.
- Change the visibility predicate to `isHidden = (layout.gridTemplate == nil)`
  in both places it appears.

Using `gridTemplate == nil` rather than enumerating layout cases means a future
layout kind cannot silently regress this.

**Files:** `Features/GridEditor/GridEditorViewController.swift`,
`Features/GridEditor/Views/GridEditorControls.swift`

### A3 · Selected cell has no visual affordance

**Problem:** selecting a collage cell enables its controls but produces no
visible change, so the selection is invisible.

**Cause:** never built for photo cells. The affordance already exists for text
overlays and stickers — a `CAShapeLayer` with a dashed `Theme.Color.accent`
stroke at `lineWidth: 1.5`, toggled by an `isSelected` property.

**Fix:** give `CellView` the same `selectionLayer` treatment, so selection looks
identical across all three object types.

For non-rectangular cells the stroke path must follow
`clipShape.path(in: bounds)` rather than a rounded rect, or the outline will not
match the visible cell edge.

Export safety: `CanvasView` is preview-only; export composites through
`CollageRenderer`. The selection layer cannot reach an exported image.

**Files:** `Features/GridEditor/CanvasView.swift`

### A4 · Border and corner-radius caps are too low

**Problem:** the caps prevent the padding and rounding users expect from a
collage app.

**Cause:** hardcoded absolute maxima — `borderSlider.maximumValue = 20` and
`cornerSlider.maximumValue = 80` — against a 1080×1080 reference canvas. Border
tops out at 1.9% of canvas width. Corner 80 cannot round a 2×2 cell (540px) past
roughly 15%, so a pill or circular cell is unreachable.

**Fix:** derive the maxima from the canvas and layout instead of hardcoding.

- Sliders become 0–1 normalized and are scaled at read time.
- Border maximum ≈ 12% of the canvas's smaller side (≈130pt at 1080).
- Corner maximum ≈ half the smallest cell's smaller side, so any cell can reach
  fully round.

This also fixes the latent problem that fixed caps behave differently on a
1080×1920 Story canvas than on a square one, and it makes squeezing a cell to
zero width unreachable by construction.

`GridEditorState.borderWidth` and `.cornerRadius` remain absolute points, so the
Codable implementation and its decoder defaults are untouched and existing
persisted projects load unchanged.

**Files:** `Features/GridEditor/GridEditorViewController.swift`,
`Features/GridEditor/GridEditorViewModel.swift`

**Tests:** cap derivation across canvas presets and cell counts; assert the
derived border can never reduce a cell to zero.

## Batch B — feature work

### B1 · Polygon border and corner radius

**Problem:** border and corner radius have no effect on polygon collages.

**Cause:** deliberate, not a bug — but undocumented and unplanned.
`CollageLayoutEngine` contains
`let insetRect = cell.clip.isRectangle ? scaled.insetBy(dx: inset, dy: inset) : scaled`,
so non-rectangular cells skip the border inset entirely. `CellClipShape.path`
documents corner radius as `applied only to .rectangle`. `insetBy` is rect-only
math, which is the real reason.

Preview and export agree today (both ignore it), so there is no
preview/export mismatch to untangle — only a missing capability.

**Fix:**

- Border: scale the polygon path about its own centroid to produce the requested
  gap.
- Corners: replace each vertex with a quadratic curve at the requested radius.
- Implement inside `CellClipShape.path(in:cornerRadius:)` so preview and export
  inherit it from one place — `CollageRenderer` already calls that method and
  needs no separate change.
- Remove the now-incorrect `applied only to .rectangle` documentation.

**Known limitation:** centroid scaling is approximate for strongly concave
polygons. Tight-angled templates need a visual check on device.

**Files:** `Core/Models/CellClipShape.swift`,
`Core/Rendering/CollageLayoutEngine.swift`

**Tests:** inset geometry (area shrinks, centroid preserved, no
self-intersection) and vertex rounding across the shipped polygon templates.

### B2 · Carousel direct export and share

**Problem:** carousel export is wrapped into a single artifact rather than
producing usable slides.

**Cause:** `CarouselExporter` exposes only `writeFrames`, `exportImageSet`, and
`zip(folder:to:)` — a carousel exits as a zip file, which cannot be posted.
`PhotoLibrarySaver` has only singular `saveImage(_ data:)`; there is no batch
path at all.

**Fix:**

- Add ordered batch save to `PhotoLibrarySaver`. Calls must be sequential and
  individually awaited — concurrent `performChanges` does not guarantee creation
  order, and ordering is the entire point for Instagram carousel sequencing.
- Add a share-sheet path accepting the image array.
- Keep the zip path for users who want files; it stops being the only option.

**Files:** `Core/Services/PhotoLibrarySaver.swift`,
`Core/Services/CarouselExporter.swift`,
`Features/CarouselEditor/CarouselPreviewViewController.swift`,
`Features/Export/UniversalExportSheetView.swift`

**Tests:** batch-save ordering.

## Batch C — Home navigation restructure

**Problem:** the module chooser is five `UIBarButtonItem`s packed into
`navigationItem.rightBarButtonItems` (New, Templates, Custom Size, Carousel,
Video) — five tap targets sharing half a nav bar.

**Target structure:** a `UITabBarController` with four
`UINavigationController` children and a floating "+".

```
Home | Templates | (+) | Projects | Carousel
```

- **Home** (new screen) — featured template strip, plus quick-start tiles for
  Grid / Polygon / Video. Custom Size is deliberately absent; it lives in the
  "+" sheet.
- **Templates** — existing gallery, unchanged.
- **Projects** — the existing project gallery, lifted out of
  `HomeViewController` largely as-is.
- **Carousel** — existing carousel entry flow.
- **"+"** — floating button in a passthrough hit-testing container above the
  bar. Opens a sheet: Image / Video / Custom Canvas → photo picker → editor with
  a default layout. Grid vs Polygon vs Freeform is then chosen from the editor's
  existing Layout and Shape pickers rather than up front.

`AppCoordinator` already owns all routing through closures
(`onNewProject`, `onBrowseTemplates`, `onNewCarousel`, `onNewFreeform`,
`onNewVideoCollage`, `onOpenProject`, `onDeleteProject`). These get rewired, not
rewritten — no editor logic changes.

Pushed editors set `hidesBottomBarWhenPushed = true`.

**Risks, explicitly:**

1. **UI tests will break.** The suite keys off `newProjectButton`,
   `templatesButton`, `freeformButton`, `carouselButton`,
   `videoCollageButton`. Carry the same accessibility identifiers onto the
   equivalent new controls so most tests need only a navigation-path update
   rather than a rewrite.
2. **`hidesBottomBarWhenPushed` vs the editor's bottom controls scroll view**,
   which is pinned to `safeAreaLayoutGuide.bottomAnchor`. Expected to be fine
   precisely because the bar is hidden, but this is a device-only failure mode.
   It goes on the QA list; it is not assumed working.

## Sequencing rationale

Batch C is last. The other six fixes live inside the editor and are unaffected
by the tab bar, so deferring C churns the UI tests once instead of twice. The
tradeoff accepted: the new Home is not seen on device until late.
