## 0. What the audit found

Grep-level audit of the 164 app sources against the phase checklist. The
numbers are the evidence the design below is sized to.

| Checklist item | State | Evidence |
|---|---|---|
| VoiceOver labels + hints | 🟡 partial | 54 labels, **1** hint, 0 custom actions. Bar buttons, tool rail, tabs, timeline controls and carousel frames are labelled. |
| VoiceOver canvas | 🔴 missing | `CanvasView.swift` contains no accessibility code. Photo cells, text zones and stickers do not exist to VoiceOver. Sticker delete is double-tap only; resize and rotate are pinch only; text and stickers move only by drag. |
| Custom rotors (Cells, Frames) | 🔴 missing | 0 sites. |

Existing labels are English literals (`"Undo"`, `"Export"`, `"Frame \(n)"`) —
the same 6.4 leftover as the rest of the UIKit copy.

## 1. Goals and non-goals

**Goals**
1. Every checklist item is either enforced by a test or recorded as a dated
   manual sign-off with the exact Settings toggles used.
2. A VoiceOver or Switch Control user can complete the first-export flow:
   onboarding → pick a layout → fill a cell → export.
3. Everything an eye can do on the canvas, a screen reader can do: inspect,
   select, edit, move, resize, rotate, delete.

**Non-goals**
- Localizing the ~130 pre-existing UIKit literals. That stays a pre-submission
  pass. Only lines this phase touches get localized, because it is cheaper to do
  it while on the line than to come back.
- Visual redesign. Where a target grows to 44pt the glyph stays its size.
- Button Shapes for custom chips, rotors for text and stickers, on-device
  hardware passes — see §10.

## 2. Approach: the audit is a test

The checklist says "verify with Accessibility Inspector" three times. iOS 17's
`XCUIApplication.performAccessibilityAudit(for:)` runs the Inspector's audit
in-process — element descriptions, hit region, Dynamic Type, contrast, clipped
text, traits — so the verification becomes a test that runs every time.

`AccessibilityAuditUITests` has one test per surface. Each navigates there using
the existing identifiers (the `VisualWalkthroughUITests` route, extended) and
calls `performAccessibilityAudit(for: .all)` with an issue handler. The handler
returns `true` (ignore) only for issues listed in a single `KnownIssue` table in
the test file, each entry carrying the element, the audit type and the reason.
An empty table is the goal; the table is where an accepted exception lives so
it is a decision rather than a silence.

Surfaces: Home · Collage tab · Carousel tab · Projects · "＋ Start Editing"
sheet · grid editor (with a panel open) · sticker picker · text style sheet ·
video editor (timeline expanded) · carousel editor · export sheet · paywall ·
onboarding (first beat) · special offer.

The audit is run **red first**. Its failure list, not §0, is the fix list for
the chrome; §0 exists so the plan can be sized before the run.

Alongside it, a headless walker in the unit target, `AccessibilityConventionsTests`,
instantiates every design-system component and editor chrome view the existing
chrome tests already build (`EditorToolRail`, `EditorPanel`, `EditorPanelRow`,
`FilterMenuChip`, `QuickStartTile`, `TextStylePresetRow`, the timeline) and
asserts three conventions on every subview:

1. anything with the `.button` trait or a `UIControl` type has a non-empty
   `accessibilityLabel`;
2. its hit region is at least 44×44 — probed with `point(inside:)` at the
   centre ± 22, not by reading `bounds`, so an expanded hit area counts;
3. every `UILabel`/`UIButton` carrying a `Theme.Typography` font has
   `adjustsFontForContentSizeCategory == true`.

The walker is fast and precise where the XCUI audit is broad and slow; both are
kept.

## 3. The canvas under VoiceOver

### 3.1 Elements

`CanvasView` becomes an accessibility container. `CellContentView`,
`TextOverlayView` and `StickerOverlayView` each become an accessibility element
(`isAccessibilityElement = true`); the container's `accessibilityElements`
orders them cells first (layout order), then text zones, then stickers — the
z-order a sighted user reads. Each view computes its own label, value, hint and
traits from the model the canvas already hands it; nothing new is stored.

| Object | Label | Hint | Traits |
|---|---|---|---|
| Empty cell | "Empty cell 2 of 4" | "Double-tap to choose a photo." | `.button` |
| Filled cell | "Photo cell 2 of 4" | "Double-tap to edit." | `.button`, `.image`; `.selected` when selected |
| Text zone | "Text: “<content>”" — or "Empty text" | "Double-tap to edit the text." | `.button`; `.selected` when selected |
| Sticker | "Sticker: <name>" — or "Personal sticker" for image-backed ones | "Double-tap to select." | `.button`; `.selected` when selected |

Labels carry the object's index ("2 of 4") because a rotor or swipe through
four identical "Photo cell" elements gives the user no position.

### 3.2 Activation

Each element overrides `accessibilityActivate()` and calls a closure the view
controller wires — `onCellActivated(index)`, `onTextActivated(id)`,
`onStickerActivated(id)` — which route into the same code the tap recognizers
reach today (`selectCell` / `presentPhotoPicker`, `onTextTapped`,
`onStickerSelected`). Explicit routing rather than trusting VoiceOver's
synthesized tap: it is testable headless, and it is correct while a cell swap
is pending (the tap handler's first branch), which a synthesized point-tap
would only get right by luck.

### 3.3 Custom actions

The operations that exist only as gestures today become
`accessibilityCustomActions`, so VoiceOver's actions rotor and Switch Control's
menu reach them:

- **Filled cell:** *Swap with another cell* (enters the existing long-press swap
  mode; activating another cell completes it, and the toast announces it).
- **Text zone:** *Move up / down / left / right* — nudges the normalized frame by
  2% of the canvas and commits one undo snapshot, through the existing
  `onTextChanged` + `onTextCommitted` pair.
- **Sticker:** *Delete*, *Larger*, *Smaller* (±10% scale), *Rotate left / right*
  (±15°), *Move up / down / left / right* — through `onStickerChanged`,
  `onStickerCommitted`, `onStickerDeleted`.

The action bodies are the gesture handlers' end states, so they share the
clamping and snapshot rules already tested for gestures.

### 3.4 Rotors and announcements

- `CanvasView.accessibilityCustomRotors` exposes a **Cells** rotor that walks
  the cell elements in layout order.
- The carousel editor's frame navigator exposes a **Frames** rotor over its
  `CarouselFrameCell`s.
- `UIViewController+Feedback.showToast` posts its text as a VoiceOver
  announcement. One site covers "Cells swapped", "Tap another cell to swap" and
  every other toast.
- Selection changes update the `.selected` trait and post `.layoutChanged` with
  the newly selected element so focus follows a rail-driven selection.

### 3.5 The video canvas

`VideoCanvasView` gets the same treatment for its cell views: "Empty video
cell 1 of 2" / "Video cell 1 of 2", hint, `.button`, activation closure. No
overlays live there today.

## 4. Dynamic Type

**SwiftUI.** The 21 `.system(size:)` sites become semantic styles
(`Font.themeBody` and friends, or `.system(.largeTitle, design: .rounded)
.weight(.heavy)`). Display sizes with no semantic equivalent (the 44–68pt
numerals on the paywall, special offer and onboarding) use
`@ScaledMetric(relativeTo: .largeTitle)` so they still scale. The rule: no
literal size without a `@ScaledMetric` behind it.

**UIKit.** Every `UILabel`, `UIButton` and `UITextField` given a
`Theme.Typography` font sets `adjustsFontForContentSizeCategory = true` at the
same line. The conventions walker (§2) enforces it on design-system components;
the XCUI `dynamicType` audit catches the rest.

**Compact controls at accessibility sizes.** The tool rail's buttons and the
timeline's chevron/play controls set `showsLargeContentViewer = true` with a
`largeContentTitle` and `largeContentImage`, which is Apple's answer for controls
that cannot grow with the text.

**Deliberate exceptions**, recorded in the walker's allow-list: collage text on
the canvas (`TextRendering` — the user's artwork, not UI) and the safe-zone
overlay captions (`SafeZoneOverlayView` — canvas annotation drawn at canvas
scale).

**Verification** beyond the audit: `AccessibilityWalkthroughUITests` launches
with `-UIPreferredContentSizeCategoryName UICTContentSizeCategoryAccessibilityXXXL`
and captures the same surfaces as `VisualWalkthroughUITests`, asserting only
that the route completes — the screenshots are the sign-off artefact for
"no layout breakage at the largest size".

## 5. Tap targets

`Theme.Layout.minimumHitTarget = 44`. Two mechanisms, chosen per control:

1. **Grow the control, keep the glyph** where the control is a plain size
   constant: `EditorPanelRow.minimumHeight` 36 → 44; the timeline header
   controls become 44pt wide with the glyph centred; the SwiftUI trim handles
   keep their 16pt bar but pad the drag gesture's `.contentShape` to 44pt.
2. **Expand the hit area** where the visual must stay small: a
   `HitTargetButton: UIButton` subclass whose `point(inside:)` insets `bounds`
   outward to 44×44. Used by the panel close (28pt circle), the camera close
   (40pt) and any other glyph-only button the audit flags.

The XCUI `hitRegion` audit and the walker's `point(inside:)` probe verify both.

## 6. Reduce Motion, Bold Text, Increase Contrast

**Reduce Motion.** Review the 19 animation calls outside `Theme.Motion`. Rule:
durations go through `Theme.Motion.duration`; springs through the
`effectiveSpring*` pair; anything repeating or auto-advancing checks
`Theme.Motion.isReduced` (the rail's symbol effects and the paywall already do).
Cross-fades stay — Apple's guidance is to replace motion with fades, not with
nothing.

**Bold Text.** `Theme.Typography.rounded` builds on `UIFont.systemFont(ofSize:weight:)`,
which the system emboldens itself. Nothing to build; verified manually
(Settings → Accessibility → Display & Text Size → Bold Text) and recorded.

**Increase Contrast.** `Theme.Color.dynamic(light:dark:)` gains optional
`lightHigh:darkHigh:` values resolved when `traits.accessibilityContrast == .high`.
Tokens that get a variant: `textSecondary`, `accent`, `separator`/borders, and
the placeholder inks — the ones sitting between 4.5:1 and 7:1 today.
`ThemeContrastTests` gains a high-contrast block pinning primary and secondary
ink to **AAA (7:1)** and every non-text pair to 4.5:1 under `.high`, in both
appearances.

## 7. Switch Control

Nothing Switch-Control-specific is built; it consumes the same elements, traits
and custom actions as VoiceOver. Verification is manual on the simulator
(Settings → Accessibility → Switch Control, keyboard as the switch): run
onboarding → "＋ Start Editing" → grid → fill a cell → export → Photos. Recorded
with the date in the sign-off doc (§9).

## 8. Localization of the new strings

Every new label, hint and action title is written as `String(localized:)`, and
the catalog is filled for all eleven languages in the same commit —
`LocalizationTests` fails an empty stub, as `5fe6afa` showed. Labels with a
position use `%lld` ("Empty cell %lld of %lld"). Existing English literal
labels on lines this phase touches (Undo, Redo, Export, Close, Direction, Add
Frame, Frame N, Clip N, Play/Pause, Expand/Collapse timeline) are localized in
passing. Expected: 40–60 keys.

## 10. Batches

Each batch is one commit on `dev`, tests first.

- **A — the harness, and what it flags on the chrome.** `AccessibilityAuditUITests`
  + `AccessibilityConventionsTests` run red; fix labels, hints, hit regions
  (§5), clipped text and traits until green. `HitTargetButton`,
  `Theme.Layout.minimumHitTarget`, localized labels for the lines touched.
- **B — the canvas.** §3 in full: elements, activation, custom actions, rotors,
  announcements, the video canvas; `CanvasAccessibilityTests`,
  `VideoCanvasAccessibilityTests`, the VoiceOver-shaped UI test.
- **C — Dynamic Type.** §4: the SwiftUI sweep, the UIKit flag sweep, large
  content viewer, `AccessibilityWalkthroughUITests` at AX-XXXL.
- **D — contrast, motion, sign-off.** §6 tokens and tests, the Reduce Motion
  bypass review, the manual sign-off doc, `Steps/STEPS_INDEX.md` (Step 06 row
  and a Phase 6.5 note) and `docs/step-06-account-gated.md` (nothing in 6.5
  needs the account; say so).

**Deferred, recorded here so it is a decision:** rotors for text zones and
stickers (the Cells and Frames rotors are the brief; the actions rotor already
lists every custom action); Button Shapes on custom chips (`FilterMenuChip`,
`QuickStartChip` — the audit does not check it and stock `UIButton`s handle it
themselves); on-device VoiceOver and Switch Control passes, which are the
owner's, like every other hardware QA in this project.
